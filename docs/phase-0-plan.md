## 1. 产品定位

**一句话定位**：面向在校学生的、以「同校二手交易」为核心的可信闲置流转平台，同时预留校园生活信息（求购、失物招领、活动）的扩展位。

**差异化重点**（也是简历项目要讲的故事）：

1. **同校优先**——交易半径小、可信度高，这是陌生人二手平台做不到的。
2. **信息层级清爽**——学生用户的核心诉求是「快速找到 + 判断值不值 + 联系卖家」，不需要社交和内容流。
3. **移动端优先**——绝大多数使用场景是手机拍照发布、课间刷列表。

**关键约束**：这是真实要给别人用的产品，不是演示页面。所以「跑得起来」只是及格线，重点是**空状态、加载态、错误态、表单校验、响应式、可访问性**这六件事。

## 2. 用户角色

| 角色 | 说明 | 权限 |
| --- | --- | --- |
| 游客 | 未登录访问者 | 浏览首页、分类、列表、搜索、商品详情；**不能**收藏、发布、进入用户中心 |
| 学生用户 | 已注册登录 | 游客全部权限 + 发布商品、编辑自己的商品、修改商品状态、收藏/取消收藏、编辑个人资料、查看我的发布与收藏 |
| 管理员 | 后台账号（MVP 由 seed 写入，不做注册入口） | 查看用户列表、封禁/解封用户、查看全部商品、下架/恢复/删除商品、管理分类 |

**权限实现原则**：前端做体验层的路由守卫与按钮隐藏，**真正的权限判断一律在后端**（否则越权漏洞会成为简历项目的减分项）。

## 3. 核心用户流程

**主流程（验收线）**

```
注册/登录 → 浏览/搜索商品 → 查看详情 → 收藏商品
    ↓
发布商品（上传图片）→ 查看我的发布 → 修改商品状态（在售/已售/下架）
```

**买家路径**：首页 → 搜索或选分类 → 列表（筛选/排序/翻页）→ 详情 → 收藏 → 通过联系方式联系卖家

**卖家路径**：登录 → 发布（图片+名称+分类+价格+描述）→ 我的发布 → 状态管理（卖出后改「已售」）

**管理员路径**：后台登录 → 商品列表（搜索/筛选）→ 下架违规商品；用户列表 → 封禁异常账号

## 4. MVP 功能范围

### 4.1 本期做（In Scope）

1. 邮箱 + 密码注册/登录，登录态持久化
2. 首页：Logo/平台名、搜索框、分类入口、最新闲置、快捷入口、平台简介
3. 6 个固定分类：数码产品、书籍资料、生活用品、服饰鞋包、学习用品、其他
4. 商品列表：分类筛选、关键词搜索、按发布时间/价格排序、分页
5. 商品详情：多图轮播、名称、价格、描述、发布时间、卖家信息、商品状态、收藏按钮
6. 发布商品：多图上传、名称、分类、价格、描述、表单校验
7. 用户中心：基本资料、我的发布、我的收藏、编辑资料、商品状态管理
8. 商品状态：在售 / 已售 / 下架
9. 图片上传：走对象存储抽象层，不落后端本地磁盘

### 4.2 本期不做（Out of Scope，明确封存）

求购信息、失物招领、校园活动、举报、消息通知、私信聊天、用户评价、信用体系、微信登录、手机验证码、推荐算法、邮箱验证与找回密码。

### 4.3 范围守卫规则

任何「顺手加一下」的想法，先记录到本文档的「待评估」清单，**不进入当期开发**。技术复杂度上升时，优先砍功能，不砍质量项（空状态/错误提示/移动端）。

## 6. 数据模型设计

### 6.1 ER 关系

```
users 1──N items 1──N item_images
  │            │
  │            └──N favorites N──1 users
  │
  └──N favorites

categories 1──N items
admins 复用 users（role=admin）
admin_actions N──1 users（记录后台操作）
```

### 6.2 表结构

**users**

| nickname | varchar(20) | 展示名 |

**categories**

| 字段 | 类型 | 说明 |
| --- | --- | --- |

### 6.3 索引与查询策略

| 索引 | 用途 |
| --- | --- |
| `items(status, published_at DESC)` | 默认列表页 |
| `items(category_id, status, published_at DESC)` | 分类筛选 |
| `items(seller_id, created_at DESC)` | 我的发布 |
| `favorites(user_id, created_at DESC)` | 我的收藏 |
| `items` 上 `pg_trgm` GIN(title, description) | **中文关键词搜索** |

> ⚠️ **重要技术决策**：PostgreSQL 默认的全文检索（tsvector）对中文分词支持很差，直接用会搜不到东西。MVP 采用 `pg_trgm` + `ILIKE '%关键词%'`，这是当前性价比最高且对中文可用的方案；数据量上万后再评估引入专业分词。

## 7. API 设计（RESTful）

统一前缀 `/api`。统一响应信封：

```jsonc
// 成功
{ "data": {...} }
// 列表
{ "data": [...], "meta": { "page": 1, "pageSize": 20, "total": 137 } }
// 失败
{ "error": { "code": "ITEM_NOT_FOUND", "message": "商品不存在或已下架", "details": [] } }
```

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| POST | `/auth/register` | 公开 | 注册并直接登录 |
| POST | `/auth/login` | 公开 | 返回 token |
| POST | `/auth/logout` | 登录 | 清除登录态 |
| GET | `/auth/me` | 登录 | 当前用户 |
| GET | `/categories` | 公开 | 启用的分类 |
| GET | `/items` | 公开 | 支持 `q, category, sort, status, sellerId, page, pageSize` |
| GET | `/items/:id` | 公开 | 详情（含图片、卖家公开信息） |
| POST | `/items` | 登录 | 发布 |
| PATCH | `/items/:id` | 本人 | 编辑 |
| PATCH | `/items/:id/status` | 本人 | 改状态 |
| DELETE | `/items/:id` | 本人 | 软删除 |
| POST | `/favorites/:itemId` | 登录 | 收藏 |
| DELETE | `/favorites/:itemId` | 登录 | 取消收藏 |
| GET | `/users/:id` | 公开 | 卖家主页信息 |
| PATCH | `/users/me` | 登录 | 编辑资料 |
| POST | `/uploads/images` | 登录 | 上传图片，返回 `{url, key}` |
| GET | `/admin/stats` | 管理员 | 概览数据 |
| GET | `/admin/users` | 管理员 | 用户列表 |
| PATCH | `/admin/users/:id/status` | 管理员 | 封禁/解封 |
| GET | `/admin/items` | 管理员 | 全部商品 |
| PATCH | `/admin/items/:id/status` | 管理员 | 下架/恢复 |

**分层约定**：`router（路由与中间件） → controller（参数校验、组装响应） → service（业务规则、权限判断） → repository/Prisma（数据访问）`。业务规则只写在 service 层，保证 API 与业务逻辑分离。

## 8. 技术架构

### 8.1 技术栈

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | Vue 3 + Vite + Vue Router + Pinia + Axios | 需求指定；组合式 API 便于拆分逻辑 |
| 样式 | 原生 CSS + CSS 变量设计令牌 + 自制基础组件 | 见 8.3 |
| 后端 | Express 5 + TypeScript | 结构透明、可控，简历上容易讲清分层 |
| 校验 | Zod | 前后端共享同一份 schema（放 packages/shared） |
| ORM | Prisma | 迁移清晰、类型安全，面试认可度高 |
| 数据库 | PostgreSQL | JSON 支持、索引能力强、免费额度好拿 |
| 鉴权 | JWT + bcrypt | 登录态简洁，无需 session 存储 |
| 图片 | 对象存储抽象层（开发：本地磁盘 / 生产：S3 兼容） | 满足「不长期存后端本地」的要求 |
| 测试 | Vitest + Supertest（API）+ Playwright（E2E 冒烟） | |
| 部署 | 单 Node 服务（同源托管）+ Neon + Cloudflare R2 | 低成本、零跨域 |

### 8.2 关键架构决策：生产环境同源部署

```
                     ┌──────────────────────────────┐
   浏览器  ────────▶ │  单个 Node 服务 (生产)          │
                     │  ├─ /            → web SPA 静态 │
                     │  ├─ /admin       → admin SPA    │
                     │  ├─ /api/*       → REST API     │
                     │  └─ /uploads/*   → 对象存储回源  │
                     └──────────┬───────────────────┘
                                │
                     ┌──────────┴──────────┐
                     │  Neon PostgreSQL    │  Cloudflare R2
                     └─────────────────────┘
```

**为什么这样做**：前后端分域名部署会带来 CORS 预检、Cookie 的 `SameSite` 跨站限制、生产/开发环境差异三类问题，是最容易吃掉一整天时间的地方。同源部署后这些问题**从根上不存在**，同时免费额度更友好、用户只需要一个访问地址。开发环境用 Vite `proxy` 把 `/api` 转到本地后端，行为和线上保持一致。

### 8.3 视觉与设计系统（不做课程作业风格）

**设计令牌**（`styles/tokens.css`，一处定义全局复用）：

- **主色**：一个克制的青蓝/靛蓝（如 `#2563eb` 系），用于主按钮、链接、选中态；**不滥用渐变**
- **中性色**：9 级灰阶，承担 90% 的界面
- **语义色**：成功（在售）/ 警示（已售）/ 中性（下架）
- **间距**：4px 基准刻度（4/8/12/16/24/32/48）
- **圆角**：8px 卡片 / 6px 控件，统一不混用
- **阴影**：只有 2 级（卡片静止、浮层）
- **字体**：系统字体栈，中文优先，字号 6 级

**自研基础组件**（避免引入重型 UI 库造成的模板感）：
`AppButton` `AppInput` `AppSelect` `AppTextarea` `AppCard` `AppTag` `AppModal` `AppToast` `AppSkeleton` `AppEmpty` `AppErrorState` `AppPagination` `AppImageUploader` `AppSpinner`

每个列表/详情页都必须显式实现 **加载态 → 空态 → 错误态 → 有数据态** 四个分支。

**分层原则**：`views` 只负责展示与交互，数据请求走 `api/`，跨组件状态放 `stores/`，可复用逻辑放 `composables/`。同一段逻辑不会在两个页面里各写一遍。

## 13. 需求冲突与待澄清（重点）

以下是我在读完需求后发现的、**需要你判断而不是由我默认假设**的问题：

1. **Phase 4 的「商品审核」与 Phase 1/2 的商品状态机冲突。**
   Phase 1 的发布流程没有「待审核」态，用户发布即上架；Phase 4 又要求审核。若后期插入 `pending_review` 状态，会改动状态机、详情页展示逻辑与列表默认筛选。→ 见 **D1**。

2. **「校园」的粒度未定义。**
   单校区 / 多校区会决定是否需要 `school`、`campus` 字段以及「只看本校」筛选。字段现在加成本几乎为零，后期加需要数据迁移和 UI 改造。→ 见 **D2**。

3. **「图片不长期存后端本地」与「低成本免费部署」的组合需要第三方存储。**
   免费方案需要额外注册（Cloudflare R2 / Supabase Storage）。→ 见 **D4/D3**，并在 Phase 2.4 用抽象层隔离，避免绑定。

4. **邮箱注册但没有邮件服务。**
   若要求邮箱验证或找回密码，就必须接入第三方邮件服务（成本 + 复杂度上升）。→ 见 **D7**。

5. **「分阶段开发」与阶段粒度的冲突。**
   原 Phase 1 一次性包含 7 类页面，单阶段无法做到「每完成一步就验证」。我已拆成 1.1–1.6 六个可运行检查点（见第 10 节），保持你的编号不变。

6. **收益/计价细节未定义。** 是否允许「面议」？是否需要原价划线？MVP 建议只做固定价格，`price_cents` 已为后续预留。
